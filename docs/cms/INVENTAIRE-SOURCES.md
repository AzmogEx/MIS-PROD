# Inventaire des sources avant CMS

Audit de lecture du 25 octobre 2026, dépôt `MIS-PROD`, état initial `prod` / `e366c51`. Ce document décrit le code initial, pas des fonctionnalités CMS livrées. À intégrer au cadrage et à relier aux preuves de recette au fil de l'implémentation.

## Périmètre constaté

- Next.js 16.2.4 App Router, React 19.2.4, TypeScript 5, Tailwind 4, Motion 12, Lenis 1.3 ; rendu serveur des routes et interactions dans des composants clients.
- Huit pages publiques explicites : `/`, `/institutions`, `/entreprises`, `/particuliers`, `/contact`, `/mentions-legales`, `/confidentialite`, `/cgv`. Une 404, `/api/contact`, sitemap, robots, images Open Graph et icônes générées.
- Aucun CMS, compte, base, stockage serveur métier, worker, mesure d'audience ou test identifié initialement. Scripts existants : `dev`, `build`, `start`, `lint`, `typecheck`. Pas de configuration CI/déploiement identifiée ; la mention OVH dans les textes légaux n'est pas une preuve de l'hébergement effectif.
- Contenus dans quatre modules `src/data/*`, plusieurs tableaux locaux et les JSX. Les styles sont dans `src/app/globals.css` et les classes des composants. Inter, Instrument Serif et JetBrains Mono via `next/font/google`.
- Intégration identifiée : API HTTP Resend conditionnée par `RESEND_API_KEY`. Le compte, domaine d'envoi, destinataire réel et hébergement ne sont pas vérifiés.

## Matrice de migration

Les écrans et modèles ci-dessous sont la cible proposée. **Toutes les lignes restent à implémenter/vérifier** tant que leur preuve n'est pas renseignée dans la recette. `E` = éditeur autorisé à modifier un brouillon ; `P` = rôle autorisé à publier ; `A` = administrateur/propriétaire pour les paramètres sensibles. Publication `V` = version publique indépendante du brouillon ; `G` = version globale publiée, avec impact sur toutes ses références ; `F` = schéma de formulaire publié, figé dans chaque demande. Aucun visiteur ne lit les brouillons.

## Données et anomalies à ne pas masquer

1. **Preuves commerciales non vérifiées.** `clients.ts` annonce explicitement des données « neutres / fictives à valider/remplacer ». Conserver les valeurs et leur origine pour migration, les signaler comme à valider. Ne pas les présenter comme des témoignages authentifiés. Les réalisations sont illustrées par Picsum ; aucun `videoSrc` n'est renseigné dans les données initiales. Les 500 projets, 8 ans d'expertise et 4,9 étoiles n'ont aucune source dans le dépôt. Le badge Best-seller n'a pas de source commerciale.
2. **Identité incomplète.** `SITE.url` retombe sur `https://mis-studio.fr`, alors que la mission cible `https://mis-prod.fr`. Adresse, SIRET, directeur et réseaux contiennent des valeurs d'attente. Le téléphone est renseigné mais encore commenté « À COMPLÉTER ». Ne pas inventer les valeurs manquantes. Les pages légales datent de mai 2026 et ne sont pas une validation juridique.
3. **Réutilisation imparfaite.** Les cartes univers d'accueil redéfinissent leurs propres contenus au lieu de lire `data/universes.ts`. Les portfolios accueil/univers peuvent désigner le même projet avec des titres/visuels différents. Une correspondance explicite est nécessaire ; ne pas fusionner uniquement par nom. Les formules génériques mariage indiquent 2 400 € alors que les tarifs dédiés proposent un vidéaste dès 790 € : périmètres différents possibles, à conserver et signaler.
4. **Formulaires non durables.** Sans clé Resend, `/api/contact` écrit l'intégralité du brief dans les logs puis confirme le succès. Avec clé, il envoie directement sans écriture métier ; une panne entraîne perte de réception. Limite d'abus en mémoire seulement ; aucune déduplication ni historique de schéma. Les types du JSON ne sont pas défendus avant les appels aux méthodes de chaîne. Les champs optionnels n'ont pas de bornes serveur.
5. **Fonctions visuelles trompeuses.** CTA showreel ouvre l'ancre réalisations ; sans source vidéo, la lightbox ouvre une image. Les 8 réalisations home ne sont pas toutes affichées : featured + les 6 premières autres. `PORTFOLIO_FILTERS` existe mais n'est pas utilisé. Le titre de formules « Quatre manières » reste affiché pour Entreprises qui en a cinq.
6. **Mobile et accessibilité.** La navigation principale masque les liens univers sous `md` sans menu mobile. La lightbox ferme avec Escape mais n'implémente ni piège ni restitution du focus. Plusieurs animations n'appliquent pas `useReducedMotion` localement ; vérifier l'effet global CSS. Les cartes univers révèlent des textes uniquement au survol. Contrastes et polices de 9–11 px méritent vérification réelle.
7. **SEO initial.** Canonical `/` défini au layout, sans remplacement par route ; sitemap à liste fixe et `new Date()` à chaque génération. Absence de données structurées identifiée. Les routes dynamiques, langues, redirections et aperçus protégés sont à construire.

## Approche de migration conservant le rendu

1. Garder les composants existants, leurs classes, ancres et interactions ; leur fournir des objets serveur typés plutôt que remplacer le site par un nouveau thème. Le renderer utilisé pour l'aperçu et le public doit être identique.
2. Extraire le texte et les tableaux locaux avec des clés stables et une provenance `fichier + clé initiale`. Conserver l'identifiant de migration et une empreinte d'import. Une réexécution ajoute uniquement les clés absentes ; elle n'écrase jamais une édition CMS.
3. Importer séparément pages, univers, réalisations, prestations/tarifs/options, clients publics, témoignages, menus et paramètres. Préserver les différences d'affichage comme variantes plutôt que les perdre. Relier explicitement les contenus réutilisés.
4. Importer les contenus existants sans les certifier. Distinguer provenance importée, exemple à vérifier et donnée authentifiée. Avant production, MIS arbitre les éléments explicitement fictifs et les preuves commerciales ; aucun remplaçant inventé.
5. Transformer les sept sections accueil et les sections univers/légales en blocs au rendu conservé. Adjoindre des blocs simples pour nouvelles compositions. Chaque texte visible, accessible, de formulaire, de succès ou d'erreur doit avoir un chemin d'édition dans la matrice.
6. Vérifier sur une base isolée avant application réelle : import deux fois, édition entre imports, comparaison texte/URL, brouillon sans effet public, publication cohérente, restauration avec médias encore disponibles. La comparaison avec le site public doit être consignée séparément ; cet inventaire n'atteste pas à lui seul de leur identité.

## Correspondances ajoutées pendant l'implémentation

L’état effectivement raccordé, les nouveaux microtextes et les limites de gouvernance sont détaillés dans la [matrice d’administrabilité actuelle](MATRICE-ADMINISTRABILITE-ACTUELLE.md). Elle distingue contenu public éditable, données métier privées et chaînes techniques du logiciel.

L'audit ci-dessus reste un relevé historique. Les textes, listes, menus, microtextes de lecteurs, identité, apparence et 404 ont été regroupés dans `src/cms/seed-content.ts`, avec champs visuels structurés dans `content-fields.ts`. Le renderer conserve les composants du site et reçoit le contenu décodé par le fournisseur commun. Les sources commerciales non vérifiées conservent leur provenance ; l'import ne les certifie pas.

Le périmètre média dispose maintenant d'un écran `/medias`, d'un scanner de références et d'un remplacement transactionnel des brouillons dans toutes les langues. Les versions publiques, historiques et publications figées gardent leurs références. L'import `scripts/cms-import-media.ts` copie les originaux publics de façon idempotente sans changer leurs chemins statiques ni réécrire les pages. Ces anciens chemins ne sont donc pas automatiquement rattachés aux copies de la médiathèque.

Les preuves métier sont dans `tests/cms-media.test.ts` (SQLite et REST réels : import, signatures, droits, originaux immuables, remplacement, quota, échéances Paris et import historique) et `tests/cms-media-import.test.ts` (fragments persistants, second processus, reprise, finalisation concurrente et lecture SQLite brute). Le fonctionnement, les paramètres et limites du stockage temporaire sont décrits dans [Imports reprenables](IMPORTS-REPRENABLES.md). La recette visuelle navigateur reste une preuve distincte de ces tests métier.
